## 分配算式里两处「与 Python 不一致」是有意的

Python 在这些输入上会**崩**或者算出**倒置矩形**, web 必须给个有限值, 所以约定
退化处理, ③ 里单独统计 (413 例除零 + 301 例中件倒置):

1. **除零** —— `200 - max(1, 后件外沿)` 分母为 0 (后件盒是 `(200,200,0,0)` 这种空盒)。
   Python: `ZeroDivisionError`。web: 退化成 `backEdge() = split`。
2. **中件倒置/零宽** —— `k_c = (split2-split1)/(b2[2]-b2[0])` 分母 ≤ 0。
   Python: 除零崩, 或 `k_c` 变号算出 `x1 > x2` 的倒置矩形。
   web: `k_c = 0`, 中件退化成 `[split1, split2]` 这条带本身。

另外注意: 矩形**越出 0-200 是正常结果**, 不是缺陷。真字形 `⿰氵工` 的左件就是
`x2 = 233.04`, `⿳一口一` 的上件到 `y2 = 248.8` —— 算式的含义是"把部件内容外沿
顶到分界线上", 部件本身窄就会被放大出画布。

## 99 引用展开: KAGE 才是权威

`99:sx:sy:x1:y1:x2:y2:name:sx2:sy2` 的接缝拉伸, 以 `kage-bundle.js` 的
`getEachStrokesOfBuhin` + `stretch` 为准:

```
缝   sp = (sx2,sy2) + 100          列9,10
目标 dp = (sx,sy)  + 100           列1,2; 但 sx>100 时先 sx-=200
若 sx>100 走"折成负偏移", 否则把缝归到中心 (sx2=sy2=0)
是否拉伸只看调整后的 (sx,sy): sx=200,sy=0 会折成 (0,0), 那就完全不拉伸
```

然后 `p < sp+100` 时 `[min,sp+100] → [min,dp+100]`, 否则 `[sp+100,max] → [dp+100,max]`。

**合法性关键**: 只要 `dp+100` 仍落在 `[min,max]` 里, 两段就都是增函数, 内容不会
跑出自己的盒子。2026-02 修掉的老 bug 就是这里 —— 老代码把列1,2 当缝、列9,10 当
目标再加 100, 于是 `130/200` 这类"右半区位置"变成 `230/300`, 冲过子件盒右沿后
右半段退化成减函数:

| 字 | 引用 | 子件盒 | 老规则落位 | KAGE 规则落位 |
| --- | --- | --- | --- | --- |
| 忽 | u5ffd-02 → 心 u5fc3-04 | x∈[18,179] | x∈[72.4, **214.9**] 越界 6 点 | x∈[72.4,183.5] 越界 0 |
| 鼻 | u9f3b-j → 自 u81ea-03 | x∈[49,151] | x∈[54.1, **274.7**] 越界 3 点 | x∈[54.1,145.9] 越界 0 |

这就是 忽 的心"反向拉伸缩成一坨"、鼻 上面有个点飞出框外的原因 —— 预览画的正是
`ids_anal.IDS()` 的输出, 而 web 渲染有 kage-bundle.js 兜着, 所以只有预览会露馅。
受影响的量级: 扫库 2,485,797 条目里 **27,137 条 (1.09%)** 含非零接缝的 99 引用。

`scripts/glyph_extend.py` 的 `unfold` 与 `trans`、`analyze_composition_v3.py` 的
`compute_stretched_bbox` 三处都已按上面的规则改正 (`diag_stretch_rule.py` 拿
26 例对拍, 最大偏差 2.8e-14)。

## 另一处数据面的坑: 畸形 99 行

库里有 **21 行** 99 引用只有 9 或 10 栏 (第三方数据 `hkcs_*` / `xicheng_*` /
`zihai-*`, 形如 `...:name:0:`)。老 `unfold` 只补 8 栏那种, 于是取 `Lp[10]` 会
`IndexError`、尾栏为空会在 `eval1` 里 `eval('')` 报 `SyntaxError`。
现在两边都按"缺栏/空栏当 0"处理 —— 这些行的 `sx,sy` 全是 0, 补齐后自然不拉伸,
与 KAGE 的行为一致 (`Math.floor(undefined)` 是 NaN, 但 `sx=sy=0` 时整段跳过)。

## 移植时踩过的另一个坑: ofs 有两档

`ids_anal.bbox` 逐笔用 `ofs=[10,5,10,5]`, 不是 `strokic_boundary` 的缺省
`[15,10,15,10]`; 差 5px, 会让左右比例整体偏一点。见 `strokeOutline.ts` 的
`BBOX_OFS`。(`ids_anal.bbox` 里 `parts[0]` 先用缺省档算了一遍, 但两档是包含关系,
并集等于 `[10,5,10,5]` 那档。)

## 速度事实 (实测, 别再拿脚本路径的数字当产品速度)

| 路径 | 冷启动 (一次性) | 每次组字 |
| --- | --- | --- |
| **web 编辑器** `renderSvg` (含 kage-bundle 出轮廓 + 拼 SVG) | 1.1 s (读 108MB + parse + 建 Map, 138 万条) | **0～4 ms**, `idsToSvg` 命中 0 ms |
| **preview 工具** | 11 s (读 248 万行 + 建索引 + 清 dbs) | **12 ms** (⿰) / 38 ms (⿲) |
| 裸脚本 `ids_anal.IDS()` | 1.3 s (读 dbs) | **8～21 s** ← 只有这条慢 |

裸脚本慢是因为 `glyph_extend.get_data` **每次调用**都在 248 万行的 list 里线性扫
(命中 0.76 s / 未命中 1.9 s), 而一次组字要查十几次 (含 `-03`/`-04` 这类退化查询,
未命中的每次都要全表扫)。**产品路径都不走这条路**: preview 把 `get_data` 换成
索引版 `_fast_get_data`, web 用 `Map`。所以"组字要几秒"只在我这种裸脚本里成立。

`layout_ref_gen.py` 现在也借 preview 的索引 (81 例 **30 分钟 → 11.6 秒**), 而且
生成的 JSON 与裸扫描路径**逐字节相同** —— 这本身就是索引精确等价的一份证据。
(索引实现就在 `preview.py`, 没有改动项目代码。)

测量脚本: `timing_paths.py` / `timing_web.cjs` / `timing_render.cjs`
(后者在 node 里把 `kage-bundle.js` 当普通脚本跑起来, 走的是真 `renderSvg`)。

前台跑长脚本**一定要加 `-u`**: 不加输出会被缓冲, 超时被杀后日志一片空白,
很容易误判成"卡住了"。

# 包围语义 (§6.6) 与变换命令

## 实现位置

- `scripts/cavity.py` —— 空腔枚举: 腔 = 容器墨迹补集里的**面** (不是最大空矩形)。
  竖条扫描精确覆盖补集 → 并查集并成面 → "面贴着墨迹外框的哪几条边" = 开口边。
  9 个算符只是 9 个"要求哪几条边封闭"的集合 (`NEED`)。
- `scripts/ids_anal.py` 的 `surround()` —— 9 个包围算符共用一条分支。
  容器取 `-05`、内部件取 `-06`, 腔交给现成的 `fit_into` + `trans`。
- `scripts/ids_anal.py` 的 `case "⿾" | "⿿"` —— 一元变换, 只追加一条命令, 不算坐标。

## 两个必须记住的约定 (都从 `kage-bundle.js` 反推)

1. **`0:9x` 命令的 `a3` 是四分之一圈计数**: 1=90°, 2=180°, 3=270° (97/98 忽略)。
   库里 `0:99:2` 出现 79 次、`0:99:1` 只有 1 次 → **⿿ 默认是 180°**。
2. **命令框要比画布宽** (`-20:-20:220:220`)。`dfTransform` 要求一条多边形的**所有**
   点都在框内才变换, 否则整条跳过; 而墨迹经常超出 0-200 几个像素 —— 用紧框就会
   "只变换一半", 这就是镜像/旋转偶发消失的原因。库里作者自己也绕这个门
   (`0:98:0:-10:-10:210:210`)。

镜像**不要**用反向矩形 (`x1=200,x2=0`): 那是对骨架镜像, 之后明朝体的起收笔调整
是方向敏感的, 实测 `日` 只镜像了一半 (墨迹 `[40,165]` → `[40,160]`, 应为 `[35,160]`)。
改用 `0:98` 命令后逐像素正确。

## ⚠️ 分段盒 (segments) 现在不可用

`stroke_boxes(..., segments=k)` 按最近骨架点给轮廓点归段, 但弯折处会漏空 ——
障碍盒覆盖不住笔画, 腔就漏到外面: 实测 **日 的两格会并成一个包住全字的大面**。
所以默认 `segments=0` (整笔一个盒, 与老 `enclosure_cavity` 同一套盒)。
要用分段, 先得证明"段盒的并集覆盖整笔"。

## 评分器

```powershell
python -u web/analysis/score_cavity.py 400              # 采样 400 个包围字
python -u web/analysis/score_cavity.py --explicit 100   # 只看带 [n] 的字
```

原理: 字 C 的 IDS 是 `⿴AB` 时, C 的真字形里有一条指向 B 变体的 99 引用,
**那条 99 的矩形就是设计者选的腔**。拿它去对候选列表, 不需要猜。

400 字实测 (segments=0):

| 默认语义 | 全部 400 | 只看有得选的 24 |
| --- | --- | --- |
| 「最大面积」(现在的默认) | 99.8% | **95.8%** |
| §6.6「#0 从上到下第一个」 | 94.2% | **4.2%** |
| 最靠近画布中心 | 96.8% | — |

→ **默认保持"最大面积"**, `[n]` 将来只作为覆盖参数, 不重定义默认。
(注: 有得选的样本只有 24 个, 方向明确但样本偏小; 枚举改进后重跑即可。)
